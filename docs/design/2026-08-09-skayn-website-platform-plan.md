# Skayn 官网与社区平台演进方案

## 1. 目标

Skayn 需要一个可以长期演进的公共入口。第一阶段是官网，负责品牌表达、产品信息、下载、安全与隐私、支持和法律文档；后续再发展为用户可以分享工具、生活经验和知识的创作者社区。

本方案的核心判断是：官网和社区是同一品牌下的两种产品表面，不应共用一个页面状态容器，也不应把社区业务直接堆进官网。

## 2. 产品边界

```text
skayn.net          公共官网：品牌、产品、下载、信任、文档
app.skayn.net      社区应用：身份、发布、互动、收藏、个人主页
api.skayn.net      平台 API：用户、内容、工具、权限、审核
status.skayn.net   服务状态：正式上线后独立提供
```

官网可以链接到社区，但不承担登录、信息流、评论或用户内容管理。社区上线前，官网不展示虚假的社区入口和未配置的联系渠道。

## 3. 推荐技术架构

### 3.1 公共官网

- Astro + TypeScript，静态输出为默认模式。
- `src/pages/` 管理真实 URL 页面，避免继续使用单个 HTML 的 hash 视图承载所有内容。
- `src/layouts/` 统一 SEO、主题、页头和页脚。
- `src/components/` 放可复用的品牌和交互部件。
- Markdown 内容集合承载隐私政策、服务条款、更新和知识文章。
- 仅把主题切换、Logo 动画、下载选择等需要交互的区域作为 islands 加载 JavaScript。

Astro 底层仍使用 Vite，可以复用当前页面的 CSS 和静态资源，不要求先引入 React 全家桶。

### 3.2 社区应用

社区是独立的 React/TypeScript 应用。它可以在同一个 Skayn monorepo 的 `apps/community/` 中维护，但不与官网共享运行时状态。

### 3.3 平台后端

初期采用模块化单体，不提前拆微服务。领域边界至少包括：

- Identity：用户、会话、个人资料
- Content：帖子、知识条目、可见性、版本
- Tool Registry：工具清单、版本、依赖、权限声明
- Social：评论、反应、收藏、关注
- Moderation：举报、审核、封禁、审计日志
- Asset：图片、附件和对象存储元数据

数据库优先使用 PostgreSQL；文件进入对象存储；搜索从 PostgreSQL 全文检索开始，规模确认后再引入专用搜索服务。队列和缓存按实际瓶颈增加，不为架构图提前购买复杂度。

## 4. 内容与信任模型

社区至少区分四类公开对象：

| 对象       | 作用                   | 重要约束                                 |
| ---------- | ---------------------- | ---------------------------------------- |
| Tool       | 可安装或复用的工具     | 版本、来源、权限、依赖和审核状态必须可见 |
| Post       | 生活记录、经验和动态   | 作者、可见性、编辑历史和举报入口         |
| Knowledge  | 可长期维护的知识内容   | 版本、引用、协作者和收藏                 |
| Collection | 对工具或内容的主题整理 | 只引用对象，不复制对象正文               |

用户分享工具属于供应链风险面。任何“安装/运行”能力都必须经过来源确认、权限展示、用户授权、隔离执行和可撤销机制；不能因为它出现在社区里就默认可信。

## 5. 目录演进

本阶段官网先保持独立项目，迁移后目标结构如下：

```text
skayn-site/
├─ src/
│  ├─ pages/
│  ├─ layouts/
│  ├─ components/
│  ├─ content/
│  ├─ styles/
│  └─ lib/
├─ public/
├─ tests/
├─ scripts/
└─ docs/
```

未来出现社区应用时，再提升为：

```text
skayn/
├─ apps/site
├─ apps/community
├─ apps/api
└─ packages/design-system, contracts, config
```

在第二个应用真正开始开发前，不提前把官网改成 monorepo，避免空目录和共享包制造维护成本。

## 6. 分阶段路线

### Phase 1：官网基础壳（本轮）

- 将单页原型迁移为 Astro 页面入口。
- 保留现有 Logo、颜色、主题切换和动态转场。
- 保持 `skayn.net` canonical/OG 配置。
- 让 Footer 只承担域名和版权，真实法律页面上线后再加入法律链接。
- 保留自动校验、格式化、构建和 CI 守门。

### Phase 2：官网内容化

- 抽取 `SiteLayout`、Header、Footer、品牌组件和全局样式。
- 把下载、安全、支持、隐私和条款拆为真实页面。
- 以 Markdown 内容集合管理法律文档和更新。
- 配置 sitemap、robots、CSP、缓存头和正式部署。

### Phase 3：社区最小闭环

- 独立社区应用和 API。
- 注册/登录、个人主页、公开帖子、知识条目、收藏和举报。
- 先支持内容分享，不开放任意代码执行。

### Phase 4：工具生态

- Tool manifest、版本、依赖、权限和来源。
- 审核、签名、隔离执行、安装前确认和撤销。
- 社区内容与工具对象通过引用关联，避免复制和分叉失控。

## 7. 本轮完成定义

- 官网源码不再依赖 Occam 项目目录。
- Astro 能够在 `npm run dev` 和 `npm run build` 下运行。
- 页面现有视觉和导航行为保持不变。
- `npm run precheck` 通过格式、结构、契约测试和生产构建。
- 方案、状态、规则和回滚路径全部落盘。

## 8. 明确不做

- 本轮不做登录、数据库、社区信息流、评论、推荐或支付。
- 本轮不接入第三方分析和未确认的支持邮箱。
- 本轮不把 Occam 后端代码复制进官网项目。
